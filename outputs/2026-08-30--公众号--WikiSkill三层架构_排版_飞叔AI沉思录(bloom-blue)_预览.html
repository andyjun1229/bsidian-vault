知识库 × 行动熔炉

前天 Google Research 发了篇论文，讲怎么让 Agent 的技能自己进化。我一开始以为是又一篇「用 AI 优化 AI」的论文，读到最后发现：它画的架构图，和我自己折腾了半年的知识库，几乎一模一样。

这篇文章我做两件事：一是把论文里没写的实操细节补上（我把三层架构在本地真搭了一遍）；二是聊聊为什么我认为这套架构验证的是一件比「技能进化」更大的事。

论文在这：arxiv.org/abs/2608.27454

01

第1章 · WHAT IT SAYS

WikiSkill 说了什么

一句话：把经验、知识、技能分成三层，让技能从知识里生长出来。

第一层 Raw Layer   —— 原始轨迹（不可变，事实依据）
第二层 Wiki Layer  —— 结构化知识（核心层，永不回滚）
第三层 Skills Layer —— 可执行技能（带溯源）

以前的技能进化方法（EvoSkill、Trace2Skill 这些），分析完执行轨迹就直接改 Skill。经验用一次就丢。WikiSkill 在中间加了一层持久知识库。每轮迭代四步：跑任务产轨迹 → Wiki 维护者做根因分析沉淀成知识 → 提案者从知识里生成技能更新 → 验证不通过就回滚（但 Wiki 保留）。

关键设计有两个。Wiki 永不回滚：技能被拒了，技能回退，但「上次为什么被拒」留在知识库里，下一轮提案者看得到，不重复踩坑。知识和技能分离：知识回答「我们知道什么」，技能回答「我们怎么做」——每个技能都带一份 PURPOSE.md，记录它是为了解决哪个知识模式而生的。

效果一句话：9B 的模型装上这套架构，跑赢了 27B 的裸模型（47.4% vs 39.4%）。去掉知识层，成绩掉 15 个百分点。

02

第2章 · HANDS ON

论文没写的部分：这套架构怎么落地

论文的架构图很漂亮，但你真要动手时会发现一堆没说的事。我花了半天在本地搭了一遍（用的就是我的知识库和 Hermes），把坑都踩了，直接给你可操作的版本。

Raw Layer：论文说「不可变」，实操是「只进不改」

论文没说原始轨迹存什么格式。实操经验：一次任务一个文件，别把多个任务塞一个日志。文件头写清楚：时间、任务、用的哪个版本的 Skill、成功还是失败。「不可变」的正确实现是目录权限，不是靠自觉——chmod -R a-w raw/，或者每次跑完直接 git commit，git 天然不可变，还能 diff。轨迹要含失败过程：最值钱的不是成功轨迹，是「我以为会成功但失败了」的那段。

一个真实教训：我早期收素材时把网页正文「精简」后入库，后来想回溯当时页面长什么样，找不回来了。Raw 层的纪律就一条：忍住别加工。

Wiki Layer：「一模式一文件 + 硬模板」

这是核心层，也是最容易做成垃圾场的一层。pattern 文件必须有硬模板——没有模板的 Wiki 会退化成心情日记。模板的作用是逼着编译过程做根因分析，而不是复述现象。我的模板四个字段：现象（什么情况触发，具体到任务类型）、根因（分析到机制层，不停在表面）、修复方案（可执行步骤，最好带代码）、关联（相关 pattern + 源头轨迹链接）。

第二，skill-impact.md 是整个系统的审计日志，必须记 diff。Agent 提案的技能改动，人是要抽查的——没有 diff，你无法判断「这个技能进化得越来越强」还是「进化得越来越会迎合验证集」。

第三，「永不回滚」要有垃圾处理机制。知识只进不出，半年就是噪音场。我的做法：30 天没被任何提案引用、且出现次数没增长的 pattern，标记 stale 不删除，移到 archive/。知识会过时，旧观点和新观点要能区分。

Skills Layer：PURPOSE.md 是最妙的文件

论文对这个文件一笔带过，但它是三层架构能自洽的关键。我给自己的每个 Skill 都补了 PURPOSE.md，除了记录「为解决哪个 pattern 而生」和设计意图，还加了一节「禁止的改动」：哪些看似合理的修改会破坏设计意图。这是实战出来的——Agent 提案的技能修改经常在技术上「更优」，但会破坏当初的约束。把负面清单写下来，提案者就不用重新踩一遍设计者踩过的坑。

进化循环：论文四步，我加第五步

论文循环：跑轨迹 → 维护知识 → 提案技能 → 门控验证。我加的是每 N 轮人工抽查一次。理由很简单——门控验证只能证明「技能在验证集上分数变高了」，证明不了「技能变得更好」。一个只优化分数的系统，最终会优化出你没想到的投机方式。这不是假设，就在几天前，OpenAI 那 700 个 Agent 已经演示过一遍了：它们花大量精力研究「怎么骗过想象中的监考官」，就因为奖励只看结果。

03

第3章 · BIGGER PICTURE

为什么我说这件事比「技能进化」大

这套架构，本质上是给「经验」建了一个资产负债表。Raw Layer 是原始凭证，Wiki Layer 是账本，Skills Layer 是根据账本做出的经营决策。以前的方法只留决策不留账本——账本丢了，决策就变成拍脑袋。

我为什么读到这篇会激动？因为我自己的知识库（raw/ → you/ → outputs/ 三层）就是这个结构：raw/ 只进不改，对应 Raw Layer 的不可变；you/ 知识持续积累，对应 Wiki Layer 的永不回滚；outputs/ 索引卡片带背景，对应 Skills Layer 的可溯源。连「听了就用 → 记一条 experience → 复盘」的工作流，都是同一个「经验→知识→行动」的闭环。

Karpathy 讲 LLM Wiki，讲的是个人知识管理；Google 发 WikiSkill，讲的是 Agent 技能进化。两边画的是同一张图：智能的持续提升，靠的不是更大的脑子，而是「经验→知识→行动」这个循环转得有多好。

这其实就是王阳明那句「知是行之始，行是知之成」的工程版。我的行动熔炉理论说：把模糊认知写成可执行规则，跑一遍，暴露漏洞，迭代。WikiSkill 做的事一模一样——只不过熔炉里炼的是 Agent 的技能，炼炉边上站着的换成了三个专门干活的 Agent。

7 年投资、半年知识库、几个月 Agent 实操，在这篇论文里汇合了。这大概就是知识库的好处：你读过的东西不会丢，它们会等着某一天互相认亲。

04

第4章 · ACTION LIST

给三类读者的行动清单

做 Agent 开发的：别再裸调 prompt 了。三层架构成本不高——git + markdown 就能搭。优先建 skill-impact.md（审计日志），它最便宜也最保值。

玩个人知识库的：检查你的库有没有「Raw 层」。只有收藏没有原始出处和日期的库，等于只有账本没有凭证，三个月后就说不清「我当时为什么觉得这个有用」。

做自媒体的：这篇本身就是选题示范——论文（外部素材）+ 自建对照（个人实操）+ 哲学连接（知行合一）= 一篇有信息增量又不干巴的文章。素材是别人的，认知是自己的。
