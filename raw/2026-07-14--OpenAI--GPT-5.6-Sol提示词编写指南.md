# GPT-5.6 Sol 提示词编写指南

在用 GPT-5.6 Sol 或 GPT-5.6 系列模型时，用此指南来适配提示词、工具描述、Agent 指令或提示词堆栈。配合当前 [GPT-5.6 模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6) 查看 API 细节、限制、定价和功能可用性。

GPT-5.6 的最佳工作方式：提示词定义好**结果**、重要约束、可用证据和完成条件，然后留出空间让模型自己选择高效的执行路径。

**删除重复的指令和示例、简化工具描述**可以提升任务性能和 token 效率。在一组内部编码 Agent 评估中，精简系统提示词的配置在评估分数上提升了约 10-15%，同时总 token 减少了 41-66%，成本降低了 33-67%。结果因工作负载而异，所以把这些范围看作方向性参考，并在你自己的应用的代表性任务上验证变化。

## 先简化提示词

从一套**已经能工作**的提示词和工具集开始。一次删除一组指令、示例或工具，然后重新运行相同的评估。

**删掉：**
- 重复表述的相同规则；
- 不改变行为的重复风格或流程指令；
- 不改变行为的示例；
- 模型已经可靠执行的流程指令；
- 与任务无关的工具和工具描述。

**保留：**
- 用户可见的结果；
- 成功标准和停止条件；
- 安全、业务、证据和权限约束；
- 依赖上下文的工具路由规则；
- 要求的输出格式和验证条件。

检查剩余指令是否有矛盾。GPT-5 级别的模型会严格遵守提示词合约，所以冲突的规则比缺少细节更容易造成不稳定。

## 结果优先的提示词与停止条件

**描述目的地，而不是规定每一步。** 当提示词说明"好的是什么样"时，GPT-5.6 通常能自己选择合适的搜索、工具或推理路径。

**推荐写法：**
```PLAIN_TEXT
端到端解决客户问题。
成功标准：
- 根据现有政策和账户证据做出资格判断
- 在回复前完成所有允许的操作
- 返回 completed_actions、customer_message 和 blockers
- 如果缺少必要证据，询问最小的缺失字段
```

**避免不必要的绝对规则。** ALWAYS、NEVER、must 和 only 只用于真正的不可变规则——如安全规则、必填字段或绝不应发生的操作。对于需要判断的决策（何时搜索、询问、使用工具、继续迭代），倾向使用**决策规则**。

**保留显式的用户价值观。** 当正确值是隐式的时，提供判断标准，让模型从上下文或结构中推理。避免通用默认值、关键词映射和宽泛的语义捷径。

**添加停止条件：**
```PLAIN_TEXT
用最少的工具循环来解决问题，但不要让"最小循环"的优先级超过正确性、必需证据、计算或必需引用。
每次拿到结果后，自问现在能否用有用的证据回答核心问题。能，就回答。不能，就说明缺少什么事实，用最小的有用回退。
```

## 人格、协作风格和回复长度

GPT-5.6 默认比 GPT-5.5 更简洁。迁移时，检查 "Be concise" 或 "Keep it short" 这类宽泛的简洁指令是否还有用。它们在某些任务中可能不再必要，有时会让回复过于简短。当它们能可靠地产出你需要的输出时就保留。

想在请求间获得更一致的风格控制，用 `text.verbosity` 设置默认详细程度，然后在提示词里指定任务级要求。在 low、medium、high 中选择请求的默认详细程度。在提示词中指定任务相关的长度、结构或必需内容。参见 [Set up text.verbosity](https://developers.openai.com/api/docs/guides/deployment-checklist#set-up-textverbosity) 的 API 示例。

**面向客户的助手和协作产品**，定义人格和协作风格两方面。

- **人格**控制语气、温度、直接程度、正式度、幽默、共情和打磨程度
- **协作风格**控制模型何时提问、做假设、主动行动、解释权衡、检查工作和处理不确定性

两者都要简短。人格塑造用户体验，协作指令塑造任务行为。两者都不应取代清晰的目标、成功标准、工具规则或停止条件。

当任务需要更短的答案时，明确模型必须保留哪些信息、可以省略哪些细节。例如：
```PLAIN_TEXT
先说结论。包含支持结论所需的证据、任何实质性注意事项和下一步行动。省略次要细节和重复。
保留所有必需的事实、决策、注意事项和下一步。先删除引言、重复、通用安抚和可选背景。
```
这给了模型一个清晰的优先级顺序：先保留完成任务所需的内容，再删减低价值细节。

**"友好"或"共情"这类宽泛标签可能含糊。** 描述定义你产品语气**具体写作选择**——比如直接陈述答案的程度、何时承认问题、安抚或结束语是否合适。
```PLAIN_TEXT
直接陈述答案。如果用户报告了问题，先承认具体问题再给下一步。只在相关时才使用安抚。省略通用的表扬和不必要的结束语。
```

**避免笼统的语言规则**（如"始终用用户的语言回复"），除非这确实是产品需求。明确指定目标输出语言以及何时切换语言。

**对于编辑、重写、摘要和面向用户的草稿**，告诉模型要保留什么：
```PLAIN_TEXT
首先保留请求的产物、长度、结构、体裁和事实主张。改进清晰度、流畅度和正确性，不要添加新主张、新段落或更推销的语气（除非被要求）。
```

## 定义自主权和审批边界

GPT-5.6 在执行多步骤任务时可能会主动且执着。定义每个请求授权的操作级别，以便模型能在安全范围内继续工作而不必要地停顿，同时在外部的、破坏性的、高成本的或范围扩大的操作前停下来。

一个紧凑的策略通常就够了：
```PLAIN_TEXT
对于要求回答、解释、审查、诊断或规划的请求，检查相关材料并报告结果。除非请求也要求实施变更，否则不做任何改动。
对于要求更改、构建或修复的请求，执行请求范围内的本地更改，运行相关的非破坏性验证，不需要事先请示。
需要确认后才能执行的操作：外部写入、破坏性操作、购买或实质性范围扩大。
```

明确列出安全的本地操作（如读取文件、检查日志、编辑范围内的代码、运行测试）。把策略放在一个地方，每条规则只说一次。"先请示""不能修改""等批准"这类重复指令会导致安全、预期内的操作也被要求不必要的审批。

**对于长时间运行的工作**，定义当前的工作层次。区分研究、设计、实现、审查和外部协调，这样模型不会无声明地从一个层次跳到另一个。

## 工具路由

只暴露与任务相关的工具。工具描述应说明工具做什么、何时使用、重要的返回值字段和错误行为。

当正确性依赖前置检索或查表时，明确说明：
```PLAIN_TEXT
在执行操作前，先完成必需的信息发现、检索和验证步骤。不要因为期望的最终状态看起来很明显就跳过前置步骤。
```

当多次读取是独立的时候，**并行执行**。当一个结果决定下一个操作时，**保持顺序执行**。并行检索后，先综合再行动。

如果工具返回空、部分或可疑的窄结果，尝试一两次有意义的回退再下结论说没有结果。

## 程序化工具调用（PTC）

**PTC 最适合有边界的、代码可以处理多个工具结果或大量中间输出并返回更小结构化结果的工作流。**

**多步、并行或依赖调用单独并不构成使用 PTC 的理由。**

**用 PTC 做：**
- 过滤、合并、排序、排名、去重和聚合；
- 在大量相似记录上的批处理；
- 重复的确定性验证；
- 可压缩为紧凑结构的大型结构化结果。

**直接工具调用更合适当：**
- 一次调用就够；
- 中间输出已经很小；
- 每个结果可能改变下一个决策；
- 某操作需要审批；
- 最终答案必须保留引用或原生产物；
- 调用之间需要语义判断。

**不要依赖通用指令**（如 "高效使用 PTC"）。明确指定边界阶段、可用的工具、输出结构、重试限制、停止条件以及交回给模型直接判断的交接点。
```PLAIN_TEXT
只在有边界的记录缩减阶段使用 PTC。只调用文档化的只读工具。过滤和去重中间结果，然后精确输出所需的紧凑结构（含证据字段）。临时失败最多重试两次。审批、语义判断、引用和最终验证用直接工具调用。
```
如果两种路径都需要，定义一个清晰的交接点，并告诉模型不要切换路径或重复已完成的工作。

`program_output` 项和最终助理消息是**两个独立的输出**，务必测试两者。理论上，程序可能返回正确的记录而消息缺失了必填字段、引用或注意事项。

**在相同的代表性任务上比较直接调用和 PTC。** 检查最终回复是否正确、完整、包含必需证据。然后比较总 token、延迟、成本、调用次数、轮次和重试次数。只有在回复仍然通过现有评估的情况下，更低的资源消耗才算改进。

## 接地、引用和检索预算

对于**接地回答**，引用行为应该是提示词的一部分。定义什么需要支持、多少证据算够、以及证据缺失时怎么处理。没有证据不应自动变成事实性的"没有"。
```PLAIN_TEXT
对于普通问答，先用简短、有区分度的关键词做一次宽泛搜索。如果顶部结果包含足够的支持来回答核心问题，就基于这些结果回答。
只有在缺少必需的事实、负责人、日期、ID 或来源时才再调用一次检索；
用户要求穷举覆盖或比较时；
必须读取特定产物时；
或者一个重要主张否则将无证据支持时。
不要为了改进措辞、增加示例或支持非必要细节而再次搜索。
```

**对于研究和综合：**
- 只引用检索到的来源；
- 将引用附在它们支持的主张旁边；
- 将推断与有直接证据支持的事实区分标记；
- 说明来源之间的矛盾；
- 缩窄答案或报告缺失证据，而不是猜测。

**对于创意草稿**，区分有来源支持的事实和创意措辞。不要为了增强草稿的说服力而编造名称、指标、日期、路线图状态、客户成果或产品能力。

## 长工作流与状态

对于**多步骤或工具密集**的任务，在第一次工具调用前写一条简短可见的前言，然后在主要阶段变化时做稀疏的状态更新。不要要求模型叙述常规的工具调用。
```PLAIN_TEXT
对于多步骤任务，在工具调用前发送一两句用户可见的更新，说明第一步是什么。任务执行中，只在一个主要阶段开始或发现改变了计划时才做更新。每次更新只说一个具体成果和下一步。
```

在回放历史时保留助理的阶段值，这样模型能区分评论和最终答案。如果使用 `previous_response_id`，之前的助理状态会自动保留。如果手动回放历史，保持每个原始阶段值不变。

**在达成主要里程碑后做压缩，而不是每一轮都压缩。** 压缩后保持提示词功能一致，把压缩后的内容当作不透明状态。

**持久化推理**在目标、假设和优先级在几轮间保持稳定时有用。当之前的推理不再相关时，用当前轮的行为。不要把持久化推理当作始终开启的优化——过时的推理会浪费 token、增加延迟、让模型锚定在过时的方法上。

**提示词缓存**也影响提示词构建。保持可复用的前缀稳定，避免大型系统提示词的不必要变更。只在明确改善缓存行为和成本时才使用显式缓存断点。

## 推理努力

在改变推理努力前，先建立基线。
- 保持当前 GPT-5.5 或 GPT-5.4 的推理努力作为基线。
- 在代表性任务上测试相同设置和低一档设置。
- 用 low 处理延迟敏感且质量不受损的工作。
- 用 medium 作为平衡的起点。
- 用 high 或 xhigh 仅当评估显示有意义的改进。
- 保留 max 给最难的、质量优先的工作负载，不要全局推荐。

在增加推理努力前，检查提示词是否缺少成功标准、依赖规则、工具路由规则或验证循环。

## 前端和视觉任务

GPT-5.6 有更强的布局、视觉层级和设计判断力。仍然要提供产品上下文，保留现有的设计系统，并说明重要的状态和约束。

**对于增量前端变更：**
- 检查并保留现有的设计 token、组件和模式；
- 不要添加未请求的额外功能或装饰性 UI；
- 保留响应式行为和预期状态；
- 在最终确定前渲染并检查结果。

**对于视觉、计算机使用、本地化或 OCR 任务**（空间精度重要时），有意识地选择图像细节。当额外的输入成本和延迟合理时，用 original detail 处理大型、密集或坐标敏感的图片。

## 完成前检查

给 GPT-5.6 提供能验证输出的工具，并说明什么验证是重要的。

**编码：**
```PLAIN_TEXT
变更后，运行最相关的可用验证：
- 针对变更行为的小范围测试
- 类型检查或 lint 检查（当可用时）
- 受影响包的构建检查
- 当完整验证成本过高时的最小冒烟测试
如果不能运行验证，解释原因并描述下一个最佳检查。
```

**视觉产物：**
```PLAIN_TEXT
在最终确定前渲染产物。检查布局、裁剪、间距、缺失内容和视觉一致性。修订直到渲染输出符合要求。
```

**实施计划**应包含：需求、命名的资源或文件、状态转换或数据流、验证检查、失败行为、隐私或安全考量、以及实质性影响实施方式的未解决问题。

## 建议的提示词结构

用这个结构作为复杂提示词的起点。每个部分保持简短。只在改变行为时才添加细节。
```PLAIN_TEXT
角色：[模型的功能和上下文]
人格：[语气和协作风格]
目标：[用户可见的结果]
成功标准：[最终答案前必须为真的事]
约束：[策略、安全、业务、证据和副作用限制]
工具：[用什么工具、何时用、不用什么]
输出：[章节、长度、格式和语气]
停止规则：[何时重试、回退、弃权、询问或停止]
```

## 提示词迁移工作流

在将现有应用迁移到 GPT-5.6 时：
1. **切换模型**并保持当前的推理努力；
2. 在改动提示词前运行代表性评估；
3. 删除过时的脚手架、重复指令和无关工具；
4. 只添加修复已测量回归所需的最小的、针对性指令；
5. 每次提示词或推理变更后重新运行评估。

**不要一次性重写一套能工作的提示词堆栈**——否则你无法判断行为变化来自模型、推理设置、提示词、工具集还是运行时。

当提示词出现回归时，用一小批真实追踪来调试。识别失败模式，找到可能导致问题的指令或矛盾，做手术式的编辑，然后重新运行相同案例。
