# 我逐渐理解了AI智能体的终极问题

最近花叔发了一条开源 huashu-design的预告，在X上一夜之间20多万阅读。我读完他最新的公众号文章，突然意识到一件事——

OpenClaw、Hermes、Claude Design、huashu-design，这些看起来完全不同的东西，其实都在回答同一个问题。

更准确地说，它们都在反复争论一件事：智能体到底靠什么工程方法来驱动？

三个阶段的演化

如果你把时间线拉长，会发现一个清晰的演化路径：

阶段一：工作流（Workflow）

这是最早的一波探索。

人们发现，光有LLM不够，得给它搭个"手脚"——定义好第一步做什么、第二步做什么、遇到错误怎么重试、什么时候应该停。这就是工作流引擎的诞生。

那时候我们讨论的是：工具调用、记忆管理、任务分解。核心思想是：把复杂任务拆成可执行的步骤序列。

阶段二：Skill（技能）

然后人们发现，工作流太死了。每个任务都要重新定义步骤，效率太低。

于是出现了 Skill 的概念——把常用的能力封装成可复用的模块。你要做PPT？用这个skill。你要写代码？用那个skill。就像给智能体装了一套工具箱。

Claude Code 里的 skills 系统、OpenClaw 里的 skill 机制，都是这个思路。核心思想是：通过能力封装来驱动智能体。

阶段三：Harness（驾驭/约束）

最近 Claude Code 源码泄露，暴露出 harness 这个概念。

这本质上是一套上下文管理协议——如何给智能体提供恰到好处的上下文？如何在任务切换时保持状态？如何让多个智能体协作而不混乱？

花叔的 huashu-design 本质上也是一个 harness——它不是在发明新的设计能力，而是在定义"如何让智能体可靠地完成设计任务"的一套协议。那5步品牌资产流程、那套硬规则，都是 harness 的一部分。

核心思想变成了：通过协议和约束来驾驭智能体。

但这真的是三个不同的东西吗？

表面上看，它们确实不同：

工作流关注步骤序列

Skill 关注能力封装

Harness 关注上下文管理

但如果你深挖一层，会发现它们其实在干同一件事：

都在试图解决"如何让智能体可靠地完成复杂任务"这个问题。

工作流说："我给它一张地图，告诉它每一步怎么走。"

Skill 说："我给它一箱工具，它自己选合适的用。"

Harness 说："我给它一套规则，让它在安全范围内自由发挥。"

这三句话翻译成技术语言，其实是一句话：通过某种工程化的方式，定义智能体的行为边界和决策逻辑。

为什么本质是一样的？

让我用一个例子来说明。

假设你要让智能体做一个PPT：

工作流思路：

读取内容文件

分析内容结构

选择模板

生成每一页

检查一致性

Skill思路：

调用 ppt-generator skill，传入：

内容文件

风格偏好

页数要求

花叔的方式：

检查品牌资产协议

提取品牌色值

3. 固化为

让智能体在brand-spec的约束下自由发挥

交付前跑Playwright验证

看起来很不同，对吧？

但请注意它们其实有共同点：

都有前置准备：工作流要分析内容，Skill要传入参数，Harness要提取品牌资产

都有执行约束：工作流有步骤限制，Skill有API边界，Harness有协议规则

都有质量保障：工作流有检查步骤，Skill有输入验证，Harness有自动测试

所谓的"不同方法"，本质上只是在不同层面做同一件事——定义智能体的行为规范。

工作流的幽灵

更有趣的是，那些号称"超越工作流"的新方法，骨子里还是工作流。

看看花叔那5步品牌资产协议：

Step 1 · 问

Step 2 · 搜官方品牌页

Step 3 · 下载资产

Step 4 · grep提取真实色值

Step 5 · 固化为

这难道不是工作流吗？只是它被包装成了一个 skill，然后通过 harness 的方式调用而已。

工作流没有消失，它只是下沉了。

从显式的步骤序列，变成了隐式的执行逻辑。从用户可见的流程图，变成了代码里的协议定义。

但这依然是工作流——"先做A，再做B，失败了就做C" 这个核心思想从来没有改变。

那到底什么才是本质呢？

如果工作流、Skill、Harness都只是表象，那本质是什么？

我认为本质只有一个：如何把人类的意图，可靠地翻译成智能体能理解并执行的工程规范。

这个翻译过程需要三件事：

结构化：把模糊的意图变成明确的参数、规则、协议

约束化：定义智能体的边界，不能做什么、必须做什么

可验证化：建立质量检查机制，确保输出符合预期

工作流用步骤序列来做这件事，Skill用API接口来做这件事，Harness用协议规则来做这件事。

工具在变，方法在变，但本质不变。

我们到底在争论什么？

每次看到"新方法"出现，社区都会争论：

"工作流过时了，用skill吧！"

"skill太重，用harness吧！"

"harness太抽象，还是工作流容易理解！"

但这些争论其实都搞错了重点。

重要的不是用哪个方法，而是你能不能把那三件事做好——结构化、约束化、可验证化。

花叔的 huashu-design 做对了什么？不是因为它用了 skill 或者harness的方法论，而是因为它把那5步协议做得足够细、足够可靠、足够可验证，这才是关键。

OpenClaw 为什么好用？不是因为它支持 skill，而是因为它把"如何让智能体可靠地完成复杂任务"这套机制做得足够工程化、足够可扩展。

终极问题只有一个

所以，当我们看到 OpenClaw、Hermes、Claude Design、huashu-design 这些不同的智能体或概念时，不要被它们的表象迷惑。

它们都在回答同一个终极问题：

如何让智能体像工程师一样思考，而不是像诗人一样自由？

工程师是可靠、可预测、可验证的。诗人是自由、不可预测、难以验证的。

我们想要的是工程师般的智能体——给它一个目标，它自己规划路径、自己选择工具、自己检查质量，但一切都在可控范围内。

工作流、Skill、Harness，都只是实现这个目标的工程手段。它们不是相互替代的，而是相互补充的。

优秀的系统会同时用到它们：

用 Skill 封装能力

用 Harness 定义协议

用 Workflow 编排流程

真正厉害的不是你用了哪个方法，而是你把这套组合拳打得有多好。

结语

我想说的是：工作流、Skill、Harness这些概念也不会被杀死，它们会在某一天融合成我们理所当然的一部分。

就像今天我们不会再争论"用变量还是用函数"，因为它们都是编程的基础设施。

智能体的工程方法也会变成这样——不再是我们争论的话题，而是我们默认的常识。

到那时，我们关注的不再是"用什么方法驱动智能体"，而是"智能体能帮我们创造什么价值"。
