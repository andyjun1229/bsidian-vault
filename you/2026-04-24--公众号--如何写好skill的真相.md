# 我拆解了花叔自建的skill之后发现了如何写好skill的真相

>

花叔的各种Skill之所以出色，不是因为他会写 Markdown，而是因为他理解了 Skill 的底层逻辑。

tags: [公众号, AI技术]
---

核心洞察：Skill 的本质是什么？

Skill = 你的专业知识 + 对 AI 行为的精确控制 + 可复用的工作系统

很多人写Skill 的问题在于：把它当成了知识库，或者简单的提示词模板。但真正顶级的 Skill，本质上是一个

可执行的程序

——有输入、有输出、有检查点、有异常处理、有优先级规则。

---

一、花叔的 Skill 设计哲学（从他身上学到的）

1. "AI 是实习生，不是专家"

花叔在 SKILL.md 开头就定义了角色：

>

"你是一位用HTML工作的设计师，不是程序员。用户是你的manager..."

诀窍：

给AI 一个具体的身份和关系定位，而不是泛泛的"你是一个助手"。

2. "默认值是陷阱"

花叔花了大量篇幅定义反 AI slop 清单——因为 AI 的默认输出就是训练语料的"最大公约数"，平庸且没有品牌识别度。

诀窍：

明确告诉AI

不要做什么

，比告诉它

做什么

更重要。

3. "流程即产品"

花叔把整个设计工作流拆解成：

10 步标准流程（含 4 个检查点 ）

8 阶段 Fallback 模式

5 步品牌资产协议

异常处理表

诀窍：

Skill 不是知识库，是

可执行的程序

。

二、Skill 写作的 5 层架构模型

基于对 huashu-design 的分析，我总结出一个可复用的框架：

```

┌─────────────────────────────────────────┐

│ Layer 5: 触发层 (Trigger) │

│ → 什么时候加载这个 Skill？ │

├─────────────────────────────────────────┤

│ Layer 4: 角色层 (Persona) │

│ → AI 应该扮演谁？和谁的关系是什么？ │

├─────────────────────────────────────────┤

│ Layer 3: 原则层 (Principles) │

│ → 不可违反的核心规则（按优先级排序） │

├─────────────────────────────────────────┤

│ Layer 2: 流程层 (Workflow) │

│ → 具体怎么做？步骤、检查点、异常处理 │

├─────────────────────────────────────────┤

│ Layer 1: 资源层 (Assets) │

│ → 组件、模板、参考文档、脚本工具 │

└─────────────────────────────────────────┘

```

三、逐层拆解：花叔是怎么做的

Layer 5: 触发层 —— 精准识别场景

花叔的做法：

```

在 description 里穷尽触发词

触发词：做原型、设计Demo、交互原型、HTML演示、动画Demo、

设计变体、hi-fi设计、UI mockup、prototype、设计探索、

做个HTML页面、做个可视化、app原型、iOS原型...

```

关键技巧：

列出所有用户可能用的表达方式

区分主干触发词和边缘触发词

明确不适用场景（如"生产级 Web App"就不该触发）

---

Layer 4: 角色层 —— 定义身份和关系

花叔的做法：

>

"你是一位用HTML工作的设计师，不是程序员"

>

>

"用户是你的manager，你产出深思熟虑、做工精良的设计作品"

>

>

"根据任务 embody 对应领域的专家：动画师/UX设计师/幻灯片设计师/原型师"

关键技巧：

给 AI 一个具体的职业身份（不是"助手"）

定义与用户的权力关系（上下级/合作伙伴/顾问）

明确能力边界（不是什么都能做）

---

Layer 3: 原则层 —— 优先级排序

花叔的 6 条核心哲学（按优先级）：

```

0 事实验证先于假设（最高优先级）

1 从 existing context 出发，不要凭空画

2 Junior Designer 模式：先展示假设，再执行

3 给 variations，不给「最终答案」

4 Placeholder > 烂实现

5 系统优先，不要填充

6 反 AI slop

```

关键技巧：

原则必须有编号和优先级

每条原则配触发条件（什么时候执行）

每条原则配反例（真实踩过的坑）

用检查点强制暂停

花叔的反例写法（非常有效）：

```

反例（2026-04-20 真实踩过的坑）：

-

用户："给大疆 Pocket 4 做发布动画"

-

我：凭记忆说"Pocket 4 还没发布，我们做概念 demo"

-

真相：Pocket 4 已在 4 天前发布

-

后果：返工1-2 小时

-

成本对比：WebSearch 10 秒 << 返工 2 小时

```

---

Layer 2: 流程层 —— 可执行的程序

花叔的标准流程（10 步）：

```

1. 理解需求（含事实验证）

2. 探索资源 + 抽核心资产

3. 先答四问，再规划系统

4. 构建文件夹结构

5. Junior pass（assumptions + placeholders）

6. Full pass（填 placeholder，做 variations）

7. 验证（Playwright 截图）

8. 总结（极简，只说 caveats 和 next steps）

9. 导出视频（默认带 SFX + BGM）

10. 可选：专家评审

```

每个步骤配：

检查点（必须停下等用户确认）

具体动作（不是模糊的建议）

异常处理（如果 X 发生，做 Y）

异常处理表（花叔的写法）：

|    场景    |        触发条件          |              处理动作                  |

| 需求模糊 | 用户说"随便做个设计" |        设计方向顾问模式             |

| 技术难点 |    超过现有资源能力   | Junior Designer 模式，展示假设 |

四、快速转化需求的 7 步法则

基于以上分析，这里是从需求到 Skill 的实操方法：

Step 1: 定义你的"领域边界"

问自己：

这个 Skill 解决什么问题？

什么问题它不解决？（明确排除）

用户通常在什么场景下需要它？

花叔的例子：

>

"专为「用HTML做视觉产出」的场景设计，不是给任何HTML任务用的万能勺"

>

适用：交互原型、幻灯片、动画、信息图

>

不适用：生产级Web App、SEO 网站、需要后端的系统

---

Step 2: 给 AI 一个"职业身份"

不要写：

>

你是一个帮助用户做设计的助手。

要写：

>

你是一位用HTML工作的设计师，不是程序员。

>

用户是你的manager，你产出深思熟虑、做工精良的设计作品。

>

根据任务embody 对应领域的专家：动画师/UX设计师/幻灯片设计师/原型师。

公式：

身份+ 关系 + 能力边界 + 动态角色

---

Step 3: 提炼你的"核心原则"

从你的经验中提炼 3-7 条不可违反的原则，按优先级排序。

花叔的原则来源：

真实踩过的坑（DJI Pocket 4 事件）

行业最佳实践（设计方向顾问模式）

对 AI 弱点的认知（反 AI slop）

你的做法：

回顾你做这个任务时最常犯的错误

回顾用户最常不满意的地方

把这些变成"原则 + 反例"

---

Step 4: 设计"工作流程"

把你的心智模型变成可执行的步骤。

坏写法：

>

先了解需求，然后做设计，最后交付。

好写法（花叔）：

>

"1. 理解需求（含事实验证）→ 2. 探索资源 → 3. 答四问再规划系统

→ 4. 构建文件夹 → 5. Junior pass（写assumptions+placeholders）

→ 6. Full pass → 7. 验证 → 8. 总结 → 9. 导出 → 10. 评审"

关键：

每个步骤要有明确的输入、输出、检查点。

---

Step 5: 预设"异常处理"

花叔的 Skill 有 7 种异常处理。你要问自己：

需求模糊时怎么办？

技术难题时怎么办？

用户反馈不好时怎么办？

超出能力范围时怎么办？

资源缺失时怎么办？

时间不够时怎么办？

出现错误时怎么办？

---

Step 6: 准备"资源库"

把可复用的东西提取出来：

| 类别 |          内容         |                    例子                   |

| 组件 | 可复用的代码片段 | React组件、Python函数、CSS类 |

| 模板 | 标准化的文档格式 | 报告模板、邮件模板、代码模板    |

| 参考 | 知识库和最佳实践 |      设计规范、编码规范、FAQ     |

| 工具 |      自动化脚本    |  渲染脚本、验证脚本、导出脚本    |

---

Step 7: 写"触发词"和"描述"

描述（description）

要包含：

能力概述（一句话）

触发词列表（穷尽）

主干能力（3-5 个核心功能）

Fallback 机制（需求模糊时怎么办）

可选功能（交付后的增值服务）

花叔的描述结构：

>

花叔Design——用HTML做高保真原型、交互Demo、幻灯片、动画、设计变体探索+设计方向顾问+专家评审的一体化设计能力。

>

触发词：做原型、设计Demo、交互原型...

>

主干能力：Junior Designer工作流、反AI slop清单、React+Babel最佳实践、Tweaks变体切换、Playwright验证、HTML动画→MP4/GIF导出...

>

需求模糊时的Fallback：设计方向顾问模式——从5流派×20种设计哲学推荐3个差异化方向...

>

交付后可选：专家级5维度评审...

六、花叔的"秘密武器"

最后，花叔之所以能把 Skill 写得这么好，还有几个底层能力：

1. 领域深度

他不是"懂一点设计"，而是对 Pentagram、Field.io、Kenya Hara 等 20 种设计哲学有深入理解。这让他能写出有品位的约束。

2. 对 AI 弱点的认知

他知道 AI 会：

凭记忆做断言（所以要求 WebSearch 验证）

产出 AI slop（所以写反 slop 清单）

闷头做到底（所以设检查点强制暂停）

3. 迭代思维

他的 Skill 有版本历史（v1 → v1.1），每个版本都基于真实踩坑升级。DJI Pocket 4 事件直接触发"核心资产协议"的升级。

4. 量化思维

"5-10-2-8 原则"、"成本对比：WebSearch 10 秒 << 返工 2 小时"——用数字让原则可执行。

---

总结：Skill 写作的心法

好的 Skill 不是"告诉 AI 做什么"，而是"构建一个让 AI 无法做错的系统"。

---

写在最后

其实，我第一次写 Skill 的时候，和现在的你一样——不知道从哪里开始，不知道怎么组织内容，写出来自己都不敢用。

后来我发现，不是我不会写，而是我把 Skill 想复杂了。Skill 就像一个工具，它不是用来展示你的知识有多渊博，而是用来“解决一个具体问题”。

当你把问题想清楚，Skill 自然就清晰了。

这篇文章，就是我想把这个认知传递给你。

如果你也写好了第一个 Skill，欢迎在评论区告诉我，我会为每一个认真回复的人点赞。
