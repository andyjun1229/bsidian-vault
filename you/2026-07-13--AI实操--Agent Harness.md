# Agent Harness（智能体框架）

## 一句话定义
Agent Harness是包裹大语言模型（LLM）的一整套软件基础设施，通过编排循环、工具、记忆、上下文管理等12个组件，让无状态的LLM变成可靠的生产级智能体。

## 核心要点
- 问题不在模型，而在模型周围的"那堆东西"——harness
- Harness是让AI从"会说"变成"会做"的完整系统
- 优秀的harness能让Agent性能提升76.4%（TerminalBench数据）
- 共同进化原则：模型越强，框架应该越薄
- Agent是"涌现行为"，Harness是"产生这种行为的机器"
- **OpenClaw 是 Agent Harness 的具体实现案例**——从框架到平台三阶段演进展示了 Harness 的工程化落地路径
- **AI最后一公里的关键在 Harness**：企业AI落地不是靠更好的模型，而是靠更好的 Harness 设计（工作流拆解、知识库集成、安全配置）

## 方法 / 步骤（12大组件）

### 1. 编排循环—— Agent的心跳
实现思考-行动-观察循环，即ReAct循环。整个流程：组装提示词→调用LLM→解析输出→执行工具→返回结果→重复。

关键点：
- 机械结构就是个while循环
- 所有智商都在模型身上，harness只管轮流转场
- 真正的复杂度在循环管理的"杂事"里

### 2. 工具—— Agent的手
工具以schema形式定义（名称、描述、参数类型），让模型知道自己有什么牌。

工具层职责：
- 注册、schema校验、参数提取
- 沙箱执行、结果捕获
- 结果格式化为模型可读的observations

Claude Code六大类工具：文件操作、搜索、执行、网页访问、代码智能、子Agent孵化。

### 3. 记忆—— 多个时间尺度的存档
记忆在多个时间尺度上运作：

- 短期记忆：单次会话的对话历史
- 长期记忆：跨会话持久化

实现方式：
- Anthropic：claude.md项目文件 + 自动生成的.claude/文件
- LangGraph：按命名空间组织的JSON Stores
- OpenAI：SQLite或Redis支撑的Sessions

Claude Code三级层级：
- 轻量级索引（每条约150字符，常驻内存）
- 详细主题文件（按需拉取）
- 原始transcript（仅通过搜索访问）

设计原则：Agent把自己的记忆当作"提示"，行动前先跟实际状态核对。

### 4. 上下文管理—— 无声翻车的高发区
核心问题是"上下文腐烂"：当关键内容掉在窗口中间时，模型性能暴跌30%以上。

生产环境应对策略：
- 压缩：快满时对对话历史做摘要（保留架构决策和未解决的bug，扔掉冗余工具输出）
- 观察屏蔽：藏起旧的工具输出，但保留工具调用可见
- 即时检索：维护轻量级标识符，动态加载数据（用grep、glob、head、tail，不加载完整文件）
- 子Agent委派：每个子Agent探索，但只返回1,000-2,000 token的精简摘要

目标：找到最小的高信噪比token集合，最大化期望结果出现的概率。

### 5. 提示词组装—— 模型此刻看到的世界
分层堆叠：
- 系统提示词
- 工具定义
- 记忆文件
- 对话历史
- 当前用户消息

OpenAI Codex优先级栈：
1. 服务器控制的系统消息（最高优先级）
2. 工具定义
3. 开发者指令
4. 用户指令（级联的.md文件，32 KiB限制）
5. 对话历史

### 6. 工具调用与结构化输出
现代harness依赖原生工具调用，模型返回结构化的tool_calls对象。

检查逻辑：
- 有工具调用？执行并继续循环
- 无工具调用？那就是最终答案

对于结构化输出，OpenAI和LangChain都支持通过Pydantic模型进行schema约束。

### 7. 状态与检查点
LangGraph将状态建模为流经图节点的类型化字典，通过归约器合并更新。

检查点在超步边界触发，实现：
- 中断后无缝恢复
- "时光倒流"般的调试

OpenAI四种策略：
- 应用内存
- SDK sessions
- 服务器端Conversations API
- 轻量级previous_response_id链式调用

Claude Code另辟蹊径：
- 用git提交作为检查点
- 用进度文件作为结构化草稿本

### 8. 错误处理
关键事实：一个10步的流程，即便每步成功率99%，端到端总成功率也只有约90.4%。错误会像滚雪球一样越滚越大。

LangGraph四种错误类型：
- 瞬时错误：带退避的重试
- LLM可恢复错误：将错误包装成ToolMessage返回给模型自行调整
- 用户可修复错误：中断并等待人工输入
- 意外错误：直接抛出供调试

Anthropic做法：在工具处理器内部捕获失败，作为错误结果返回，确保主循环不中断。

Stripe生产级Harness：重试次数严格限制在两次以内。

### 9. 护栏
OpenAI SDK三层防护：
- 输入护栏：在首个Agent上运行
- 输出护栏：在最终输出上运行
- 工具护栏：每次调用工具时都运行

一旦触发"绊线"机制，Agent立刻急刹车。

Anthropic架构：
- 权限执行与模型推理彻底解耦
- 模型负责"想做什么"
- 工具系统负责"能做什么"

Claude Code独立管控约40种离散工具能力，分三个阶段：
1. 项目加载时建立信任
2. 每次调用工具前检查权限
3. 高风险操作必须获得用户明确确认

### 10. 验证与反馈
这是玩具演示和生产级Agent的分水岭。

Anthropic三种验证方式：
- 基于规则的反馈：测试、Linter、类型检查器
- 视觉反馈：通过Playwright截图检查UI任务
- LLM当裁判：用独立子Agent来评估输出

Claude Code创始人Boris Cherny指出：给模型一个验证自身工作的手段，能让质量提升2-3倍。

### 11. 子Agent编排
Claude Code三种执行模式：
- Fork：父上下文的字节级精确副本
- Teammate：独立的终端面板，通过文件邮箱通信
- Worktree：每个Agent拥有独立的git工作树和隔离分支

OpenAI SDK支持：
- Agent作为工具：专家处理有边界的子任务
- 交接：专家全面接管

LangGraph将子Agent实现为嵌套的状态图。

### 12. 初始化与环境搭建
完整周期协同工作：

**步骤1（提示词组装）：** Harness构建完整输入：系统提示词 + 工具schema + 记忆文件 + 对话历史 + 当前用户消息

**步骤2（LLM推理）：** 提示词送往模型API，生成输出token（纯文本、工具调用、或两者兼有）

**步骤3（输出分类）：**
- 只生成文本无工具调用 → 循环结束
- 请求工具调用 → 进入执行阶段
- 请求交接 → 更新当前Agent并重启

**步骤4（工具执行）：** 验证参数、检查权限、沙箱执行、捕获结果。只读操作可并发，写操作串行处理

**步骤5（结果打包）：** 结果格式化为LLM可读消息，错误作为错误结果返回

**步骤6（上下文更新）：** 结果追加到对话历史，接近上下文窗口上限时触发压缩

**步骤7（循环）：** 回到步骤1，重复直到终止

终止条件：
- 模型产出无工具调用的回复
- 达到最大轮次限制
- token预算耗尽
- 护栏绊线被触发
- 用户主动中断
- 返回安全拒绝

## 企业AI落地——Harness 视角的补充（来自 [[raw/2026-04-15--公众号--最后一公里其实在政企不在消费者]]）

AI最后一公里的核心问题不在模型，而在于 Agent Harness 的企业级工程化能力：

### 企业需要的 Harness 能力
1. **工作流引擎**：不仅执行单轮工具调用，还要编排多步骤业务流程
2. **企业知识库集成**：RAG 架构 + 文档/制度/标准/案例的知识注入
3. **私有化部署**：数据不出域，支持国产化适配
4. **安全护栏**：权限管理、审计日志、合规认证
5. **持续优化**：业务分析→匹配大模型→工作流拆解→知识库建设→安全配置

### 大厂 vs 企业的矛盾
| 维度 | 大厂（SaaS） | 企业需要 |
|------|------------|---------|
| 产品形态 | 标准化产品卖给1000万用户 | 定制化方案，深度理解业务 |
| 数据 | 放云上 | 私有化，数据不出域 |
| 迭代 | 快速发新版 | 稳定可靠，不能随便改 |
| 商业模式 | 持续订阅 | 一次性+运维服务 |

这个矛盾正是 Agent Harness 服务商的机会——做大厂不愿做的"最后一公里"集成服务。

- **误区**：问题在模型，性能差就换更强的模型
  - 正确理解：问题往往在harness设计，优秀的harness能让性能提升76.4%
- **误区**：Agent就是大模型
  - 正确理解：Agent是"涌现行为"，Harness是"产生这种行为的机器"
- **误区**：搭建了框架就能用了
  - 正确理解：框架是"脚手架"，楼盖好了就该拆了。模型越强，框架应该越薄
- **误区**：OpenClaw部署好就等于有私有大模型

- **误区**：企业AI落地直接买大厂工具就行
  - 正确理解：需要定制化 Harness 方案 + 业务理解 + 工作流拆解
- **边界**：单Agent足够时，不要盲目上多Agent。只有工具重叠超过10个，或任务域明显分离时，才考虑拆分
- **边界**：harness不是万能的，真正的硬工程在于：把上下文当稀缺资源管理、设计验证循环、构建记忆系统

## 进阶概念

### Harness Engineering vs Prompt Engineering vs Context Engineering
围绕模型有三层同心圆式的工程体系（翁荔2026）：
- **提示工程（Prompt engineering）**：精心打磨模型收到的指令。
- **上下文工程（Context engineering）**：管理模型在什么时候看到什么内容。
- **Harness 工程（Harness engineering）**：涵盖以上两者，再加上整个应用基础设施——工具编排、状态持久化、错误恢复、验证循环、安全强制执行和生命周期管理。

### Framework vs Harness 的区别
Framework（如LangChain、LangGraph）是"地基和工具箱"，给你材料让你自己盖房；Harness（如Claude Code、DeerFlow 2.0）是"带装修的房子/操作系统"，开箱即用，内置最佳实践。

| 维度 | Framework | Harness |
|------|-----------|---------|
| 定位 | 地基和工具箱 | 带装修的房子/操作系统 |
| 给你什么 | 材料让你自己盖房 | 开箱即用，内置最佳实践 |
| 需要你做什么 | 自己组装、做决策 | 定制和扩展即可 |
| 代表产品 | LangChain、LangGraph | Claude Code、DeerFlow 2.0 |

Framework基本不在乎你怎么组装，意味着灵活性，但也意味着你要自己解决所有生产环境问题。Harness提供有主观立场的基础设施层，内置了上下文管理、工具执行、状态持久化和验证的默认架构。

### Harness 六大模块（六层模型）
一个完整的Harness系统包含6大核心组件（对应Anthropic提出的六层架构）：

| 模块 | 作用 | 通俗翻译 |
|------|------|----------|
| 1. 指令层 | 规则文件，定义智能体是谁、为谁服务、如何服务 | 宪法——AI不能做什么 |
| 2. 上下文层/资源层 | 信息管理，让Agent知道该看什么 | 海马体——AI记得住事情 |
| 3. 工具层/技能系统 | 能力边界，封装外部API、库和流程 | 武器库——AI能做什么 |
| 4. 边界层 | 权限控制，告诉AI哪些能干，哪些不能干 | 护栏——爆炸半径控制 |
| 5. 反馈层 | 错误提示，让Agent感受到现实 | 监控塔——看得见AI在干什么 |
| 6. 治理层 | 成本监控，让所有任务有序并发协作 | 操作系统——任务组织和管理 |

这六大组件本质上是让非确定性的大模型在确定性的框架里稳定运行。

### 七个架构抉择
每个框架架构师都要面对的七个关键决策：
1. **单智能体 vs. 多智能体**：先把单智能体榨干再说。只有当工具重叠超过约10个，或任务域明显分离时，才考虑拆分。
2. **ReAct vs. 计划-执行**：ReAct每步都把推理和行动搅在一起（灵活，但每步成本高）。LLMCompiler相比顺序ReAct有3.6倍加速。
3. **上下文窗口管理策略**：五种方案——基于时间的清理、对话摘要、观察掩码、结构化笔记、子智能体委派。优先保留推理痕迹而非原始工具输出，可减少26%-54% token消耗且保持95%+准确率。
4. **验证循环设计**：计算验证（测试、linter）提供确定性真相；推理验证（LLM当裁判）抓语义问题但增加延迟。Martin Fowler的Thoughtworks团队把这叫引导器（guides，行动前引导）vs. 传感器（sensors，行动后观察）。
5. **权限与安全架构**：宽松模式（快但险）vs. 严格模式（安全但慢）。
6. **工具范围策略**：工具越多性能越差。Vercel砍掉80%工具后效果更好。Claude Code通过懒加载实现95%上下文缩减。原则：当前步骤需要啥就暴露啥。
7. **框架厚度**：多少逻辑放框架里，多少留给模型。Anthropic走薄框架+模型进化路线。Anthropic定期从Claude Code框架中删掉规划步骤，因为新版本模型已内化该能力。

### 自我改进（Self-Improvement）
翁荔（Lilian Weng）2026年论文《Harness Engineering for Self-Improvement》的核心发现：
- **近期的自我改进路径不是改模型权重，而是改进Harness**。
- Harness本质上是代码，代码可以被AI编写，因此AI可以自己优化自己的Harness。
- 相关研究：STOP（Self-Taught Optimizer）、Self-Harness、Darwin Gödel Machine（DGM）、AlphaEvolve等。
- **关键约束：模型必须足够强，自我改进才有效**。STOP用GPT-4能持续改进，用GPT-3.5反而退化。
- 翁荔名言："Harness改进能更好地部署模型，但智能本身仍然是核心。"

### 三个设计模式（翁荔总结）
1. **工作流自动化**：按"规划→执行→观察/测试→改进"目标驱动循环跑，过程中可主动向用户澄清规范
2. **文件系统作为持久记忆**：别把所有东西塞对话里，写到文件里；日志、diff、过往轨迹远超上下文窗口
3. **子代理和后台作业**：主代理管进程管理器（启动作业、检查日志、取消失败运行、合并结果），子代理并行执行

### 优化层次
优化的对象不断升级（翁荔）：
**提示词 → 结构化上下文 → 工作流 → Harness代码 → 优化器代码**

越往后，优化空间越大，但也越难。很多"一键生成"的智能体停留在最浅层的提示词优化。

### 上下文工程（Context Engineering）

#### ACE（Agentic Context Engineering）
Zhang et al. 2025，将上下文视为演化的playbook而非不断变长的提示词。三个组件：
- **Generator**：生成任务轨迹，引用子弹笔记条目
- **Reflector**：从成功/失败轨迹中提取洞见
- **Curator**：用增量逐条方式更新结构化上下文，不重写整个blob

关键设计：curator输出结构化子弹笔记`(标识符, 描述)`，通过确定性逻辑合并。防止上下文坍塌和简洁性偏差。

#### MCE（Meta Context Engineering）
Ye et al. 2026，将机制（如何管理上下文）与工件内容（上下文里有什么）分离。双层优化：
- **内层**：给定技能s找到最佳上下文c_s*
- **外层**：找到验证集上最优的技能s*

技能数据库追踪历史`H_{k-1} = {(s_i, c_i, J_i^train, J_i^val)}^{k-1}_{i=1}`。元层级智能体执行"智能体交叉"创建新技能，基础层级上下文工程师执行该技能。上下文函数c实例化为文件集合（skill.md静态组件 + 数据rollout动态组件）。

#### Meta-Harness
Lee et al. 2026，优化的对象是"决定和优化存储什么、检索什么、向模型展示什么的代码"。Meta意为"用于优化harness的harness"：
- 提案者本身是编码智能体，最终输出Pareto前沿上的一系列harness候选
- 整个执行历史通过文件系统可访问（用grep/cat读取，不塞进提示词）
- 提案harness是文件系统中的一个字典：源代码、评分、rollout轨迹、状态更新
- 循环迭代创建新harness，只保留合格者

核心教训：一旦harness设计变成可执行搜索空间，强大编码智能体就能像人类工程师一样利用设计空间。

### 工作流设计自动化

#### AI Scientist
Lu et al. 2026，构建流水线提出研究想法→编写代码→运行实验→分析结果→撰写论文→同行评审。
**ScientistOne**（Meng et al. 2026）将可验证性作为核心约束，每个主张追溯到证据来源。

#### Autodata
Kulikov et al. 2026，设计为数据科学家智能体。主智能体管理：挑战者（提问题）、弱求解器、强求解器、验证器/裁判。目标是合成"难度刚好合适"的数据。局限：仅用于微调弱求解器而非强求解器，RSI色彩较弱。

#### ADAS（Automated Design of Agentic Systems）
Hu et al. 2025，将智能体设计形式化为优化问题：
1. 用简单智能体（CoT, self-refine）初始化工作存档
2. 元智能体用代码编程新智能体，受存档启发
3. 草稿经两个self-refine步骤
4. 评估新候选，加入成功者到存档
5. 重复达最大迭代

#### AFlow
Zhang et al. 2025，将工作流表示为图（节点=LLM调用动作，边=逻辑操作），依赖MCTS优化：
1. 用模板初始化W_0
2. 评分+均匀探索的软混合选择节点
3. LLM生成修改后的工作流来扩展节点
4. 执行并评估
5. 改进则加回树
6. 重复至top-k平均分平稳或达预算

### 进化搜索（Evolutionary Search）

#### STOP（Self-Taught Optimizer）
Zelikman et al. 2023，递归脚手架改进的早期例子。种子改进器I_0接受初始解决方案s、效用函数u、黑盒LLM M，返回改进后s'。目标不是改进s，而是改进改进器I本身：
- 元效用：`\hat{u}(I) = 1/|D| * E_{(u,s)~D}[u(I(u,s; M))]`
- 递归更新：`I_t = I_{t-1}(\hat{u}, I_{t-1}; M)`
- 改进器发现了遗传算法、分解改进、多臂提示词bandit、模拟退火、束/树搜索等策略
- 警示：GPT-4能改进，GPT-3.5/Mixtral退化——仅有递归结构不够，基础模型要够强

#### Self-Harness
Zhang et al. 2026，通过"提案-评估-接受"循环改进自身harness。三个阶段：
- **阶段1：弱点挖掘**——将失败聚合成基于验证器的失败模式，包含丰富信息的失败记录（终端验证器原因、因果状态、轨迹暴露的抽象机制）
- **阶段2：Harness提案**——基于失败模式，提交有限范围harness编辑。提案上下文：当前可编辑表面+失败模式+应保留行为+先前尝试摘要。优先可处理且反复出现的错误模式
- **阶段3：提案验证**——在held-in（测试弱点是否解决）和held-out（检查是否引入新问题）上回归测试，无回归才接受

在MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5上运行Terminal-Bench-2，验证了学习模型特定harness指令的能力。

#### 进化搜索方法
- **Promptbreeder**（Fernando et al. 2023）：通过丰富变异操作优化任务提示词，变异提示词本身也经进化改进
- **GEPA**（Agrawal et al. 2025）：将基于反思的提示词与进化搜索结合
- **AlphaEvolve**（Novikov et al. 2025）：编码智能体进化搜索，存储候选程序池，冻结LLM生成diffs改进
- **ThetaEvolve**（Wang et al. 2025）：进化搜索+强化学习+上下文学习
- **ShinkaEvolve**（Lange et al. 2025）：亲本采样平衡、代码新颖性拒绝采样（嵌入余弦相似度）、元草稿识别良好模式

#### Darwin Gödel Machine（DGM）
Zhang et al. 2025，用基于LLM的编码智能体进化可编辑的harness代码仓库。智能体被允许修改自身的harness：
1. 池中从1个编码智能体开始
2. 选父代（概率正比性能，反比已有子代数），通过修改和分支产生新智能体
3. 父代检查基准评估日志，对其harness代码库提改进（使用bash和editor两个工具）
4. 新智能体评估，性能足够高才加回池
5. 重复至停止条件

以Claude 3.5 Sonnet为基础LLM，DGM在SWE-bench Verified（20%→50%）和Polyglot（14.2%→30.7%）上媲美手工智能体。

#### Hyperagents（超智能体）
Zhang et al. 2026，引入元智能体控制如何修改现有任务智能体来创建新智能体。

### 联合优化（Harness + 权重）

#### SIA（Self-Improving AI）
Hebbar et al. 2026，在同一优化循环中结合harness改进和模型参数更新。三个组件：
- **元智能体**：提出初始harness
- **任务特定智能体**：执行任务
- **反馈智能体**：根据最近轨迹选择更新harness还是模型权重

实验中有混淆因素（任务智能体远弱于元/反馈智能体），证据仍是初步的。但方向有意义。

### 自我改进的7个挑战（翁荔，2026完整版）

| # | 挑战 | 说明 |
|---|------|------|
| 1 | **薄弱和模糊的评估器** | 大部分任务没有标准答案。研究品味、新颖性、长期科学价值难以衡量 |
| 2 | **上下文和记忆生命周期** | 记忆增长超出上下文窗口，上下文工程应成为智能核心部分而非停留在软件系统层 |
| 3 | **负面结果** | 文献偏向成功，LLM可能不擅长判断何时放弃假设/报告负面结果 |
| 4 | **多样性坍塌** | 进化/RL循环倾向于利用已知高奖励模式，最优路径在初始评估器下可能更差 |
| 5 | **奖励篡改** | 自改进循环优化任何信号——过拟合单元测试、学习针对裁判模型的技巧、利用基准伪迹 |
| 6 | **长期成功** | 外部优化循环作用于单个rollout之外的奖励，难以捕捉可维护性、所有权边界、迁移成本 |
| 7 | **人类的角色** | 人类应向上移动堆栈到更高抽象层，而非从循环中被移除 |

### 未来方向：Harness层 vs 核心智能
- Harness工程朝元方法论发展——改进获取更好答案的机制，而非答案本身
- 成熟harness使自动研究服务于模型自改进循环，更智能的模型防止harness过度工程化
- 最终很多harness改进会被内化到核心模型行为，但外部上下文和工具的接口应保留
- 类比提示词工程：随模型能力提升，手工提示词技巧变得不重要，但指定目标/约束/评估的需求没有消失

### 相关基准（Benchmarks）
以下基准用于评测AI智能体的Harness和自改进能力（来源：翁荔2026附录）：
- **PaperBench**（Starace et al. 2025）：从零复现ICML 2024 Spotlight/Oral论文。8,316条评分标准，当时最好模型（Claude 3.5 Sonnet~21%）未超过ML博士
- **CORE-Bench**（Siegel et al. 2024）：评估已发表研究的计算可复现性。90篇论文270个任务，最难任务上GPT-4o/4o-mini仅21%准确率
- **ScienceAgentBench**（Chen et al. 2025）：评估数据驱动的科学发现，4学科44论文102任务
- **RE-Bench**（Wijk et al. 2025）：评估AI智能体与人类专家对比。最好AI在2小时预算下得分比人类高4倍，但人类在8/32小时设置下反超
- **MLE-bench**（Chan et al. 2024）：离线Kaggle竞赛评估。最佳设置（o1-preview+AIDE）在16.9%竞赛中达Kaggle铜牌
- **KernelBench**（Ouyang et al. 2025）：GPU内核正确性和速度，250个PyTorch任务

### 关键原则：能用代码管的，别靠"拜托"
"请记得处理完100个文件就停" → 会被忘。MAX_FILES = 100 + raise RuntimeError → 代码执行不会忘。刚性约束是对混乱的最好防御。Hook会执行，自然语言会被忘。

### Agent = Model + Harness 核心公式

| 部分 | 作用 | 通俗翻译 |
|------|------|----------|
| Model | 大模型本身 | 马匹——提供动力和智力 |
| Harness | 包裹在模型外围的运行时控制系统 | 马具——提供方向、约束和承载力 |

如果说大模型是AI的"大脑"，那么Harness就是它的"身体"和"神经系统"。

### Harness Engineering的历史地位
软件工程30年的复杂性中心转移：对象（1994，GOF设计模式）→ 企业架构（2002，马丁·福勒）→ 分布式系统（2010，微服务）→ 数据系统（2017，DDIA）→ **智能体Harness（2026）**。2026年，复杂性中心是怎样让不确定的AI干活。

**码农 vs 工程师**：码农修一次bug，工程师消灭一类错误。码农写代码，工程师设计执行环境。码农靠个人能力，工程师靠组织能力。码农会被替代，工程师不会。

### 智能体终极问题
工作流、Skill、Harness三者不是相互替代的，是相互补充的。本质只有一个：**如何把人类的意图可靠地翻译成智能体能理解并执行的工程规范**。这个翻译过程需要三件事：结构化、约束化、可验证化。优秀的系统同时用到三者——用Skill封装能力、用Harness定义协议、用Workflow编排流程。

### 共同进化原则
模型在后训练时会把特定框架纳入训练循环。Claude Code的模型学会的是它训练时配对的那个特定框架。因为这种紧密耦合，改了工具实现反而可能导致性能下降。框架设计的"面向未来的测试"：如果模型更强了，性能自然提升，而框架复杂度不需要增加，那这个设计就是靠谱的。
Manus在半年内重构了五次，每次重写都在做减法。复杂的工具定义变成了通用的shell执行，"管理智能体"变成了简单的结构化交接。
