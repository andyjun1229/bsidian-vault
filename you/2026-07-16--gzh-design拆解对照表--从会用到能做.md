# gzh-design 拆解对照表 —— 从「会用」到「能做」

这张表是你对 gzh-design 进行拆解分析的结果。目标是从「知道怎么用」升级到「能自己做出这样的 Skill」。

## 一、整体结构拆解

| 维度 | 你以前的做法 | gzh-design 的做法 | 差距在哪 |
|------|------------|------------------|---------|
| **Skill 形态** | 一个长 prompt，全塞在一起 | 三层分离：SKILL.md（工作流决策） + references/（精确组件） + scripts/（校验脚本） | 你把所有东西丢给 LLM 自己判断，gzh-design 把 LLM 当「复读机+填表工」用 |
| **精确到什么程度** | "排一篇好看的排版" | 主题色值 `#0F172A`、`#38BDF8`、下划线 `border-bottom:2px solid #38BDF8` | 你可以让 AI 理解「好看」，但 AI 不能保证每次理解一样。精确参数锁定一致性 |
| **容错机制** | 无。LLM 出错了你不知道 | validate_gzh_html.py：自动检查 14 条禁用规则、span leaf 包裹、半角标点 | 没有校验脚本的 Skill，LLM 的精确执行错误永远不会被捕获 |
| **主题管理** | 无。每次从头写 | theme-index.md 统一登记，运行时选主题→读对应组件库 | 单一权威来源（SSOT），所有指令以它为准 |

## 二、关键设计决策（你自己能复制到下一个 Skill）

| 决策 | 为什么这么设计 | 对下一个 Skill 的启示 |
|------|--------------|---------------------|
| **SKILL.md 只做决策，不存代码** | LLM 最擅长选方案（判断文章类型、选主题），最不擅长写精确 HTML。决策让 LLM 做，执行让 LLM 照抄 | 你的 Skill 也应该分两层：LLM 判断「用什么」，然后从资产库取精确代码 |
| **组件代码精确到像素** | 所有组件库里每个 `<span leaf="">` 都写死了，LLM 只需要替换 `{{变量}}` | 下次写 Skill 时，关键代码你先写 80% 的固定部分，留 3-5 个填空位 |
| **每个主题一套独立组件库** | 7 个主题，7 套组件库，互不干扰 | 如果你的 Skill 要输出多种风格，每种风格独立文件，不要混在一起 |
| **校验脚本跑不过不出货** | validate_gzh_html.py 检查到 ERROR 就让 LLM 回去改，不交付废品 | 任何 Skill 都要有一个「不通过=不交付」的硬检查，可以是语法检查、格式检查、数据完整性检查 |
| **Gotchas 写进 SKILL.md** | 每次踩过的坑都记录为 LLM 必须遵守的规则，不是建议 | 每用一次就记一条，慢慢 Skill 就变强了 |

## 三、三个功能层的对应关系

| 你缺哪个 | 对应文件 | 代码量 | 作用 |
|---------|---------|-------|------|
| 资产层 | `references/theme-bloom-blue.md` | ~470 行 | 一个主题的完整组件库（设计变量+20个组件+模板骨架+配方+映射） |
| 校验层 | `scripts/validate_gzh_html.py` | ~170 行 | 硬检查：禁用标签、leaf 包裹、半角标点 |
| 工作流层 | `SKILL.md` | ~172 行 | 决策逻辑：选主题→读库→拼装→校验→输出 |

**关键数字：** 真正需要 LLM「创造」的部分不到 200 行。剩下 600+ 行全部是「直接复制粘贴即可」。

## 四、现存可挖掘的结构

| 现象 | 背后的设计意图 |
|------|-------------|
| theme-index.md 只有 35 行，但 7 个主题全部用它做锚点 | 单一权威来源，改一个地方所有 LLM 指令同时生效 |
| 通用组件库 common-components.md 独立于主题库 | 代码块/图片/小标签，任何主题都需要，不用每套重复写 |
| wrap_preview.py 不改变正文 HTML，只包一个预览外壳 | 干净输出 + 便利粘贴，两者不耦合 |
| 下划线色值同时出现在 theme-index 和组件库里 | 名义上 SSOT 是 theme-index，但组件库为了精确也有。这其实是设计矛盾，但实际中保持两者一致就不出问题 |

## 五、你可以立刻做的事

1. **选一个你觉得「差距最大」的方面** → 对应上面「你缺哪个」列
2. **打开对应的文件读完** → 理解它做了什么
3. **用同样的模式去改造你现在在用的 Skill**

具体来说：
- 如果你理解了三层分离 → 去看自己用的 Skill，拆成三个文件
- 如果你理解了 SSOT → 找到你 Skill 里「同一参数多处定义」的地方，归到一个文件
- 如果你理解了校验脚本 → 给你用的 Skill 加一个 25 行的 check 脚本
- 如果你不理解某个地方为什么这么设计 → 打开对应的 reference 文件读
