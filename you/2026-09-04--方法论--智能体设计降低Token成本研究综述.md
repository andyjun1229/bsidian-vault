# 智能体设计降低 Token 成本研究（2024-2026）· 详细做法与已验证案例

> 调研范围：arXiv / HuggingFace Papers 收录、有实验数据支撑的工作；按「策略→机制→验证数据」整理。
> 核心问题：**如何通过智能体（Agent）系统设计降低 token 使用成本，同时保证任务质量不降。**

---

## 零、先建立一个成本模型（所有方法的坐标系）

Agent 任务的 token 成本 = Σ(每轮调用的 输入token × 输入单价 + 输出token × 输出单价) × 轮数

由此得出六个降本杠杆，后面所有方法都挂在这六杠杆上：

| 杠杆 | 原理 | 代表方法 |
|---|---|---|
| **L1 缩短输入** | 输入 token 占 Agent 成本大头（历史+工具输出反复重发） | 上下文压缩、记忆编译、日志精简 |
| **L2 缩短输出** | 思考链越长越贵 | 推理预算控制、思维链精简 |
| **L3 减少轮数** | 多轮=多份重复输入 | 轨迹压缩、计划缓存、Agent 合并 |
| **L4 换便宜模型** | 强弱模型单价差 10-100 倍 | 级联、路由、蒸馏、小模型 Agent |
| **L5 复用计算** | 相同/相似输入不重算 | 语义缓存、KV/前缀缓存、计划缓存 |
| **L6 免调用** | 不调 API 就零成本 | 规则引擎兜底、内部化策略 |

## 一、L1 缩短输入：上下文压缩与记忆编译

### 1.1 Structured Distillation for Personalized Agent Memory（**11× token 缩减**）
- **做法**：长对话历史不逐字携带，而是蒸馏成结构化记忆条目（用户偏好、事实、决策），检索时按需注入
- **验证数据**：个性化 Agent 记忆场景 token 减少 **11 倍**，检索质量不损失
- **可抄点**：把「对话历史原文」换成「结构化记忆 + 按需检索」，是单 Agent 降本第一优先级

### 1.2 A Self-Evolving Framework for Efficient Terminal Agents via Observational Context Compression
- **做法**：终端类 Agent 的原始环境反馈（命令输出）不再全量进历史，做「观察性上下文压缩」——只保留对后续决策有信息量的部分
- **可抄点**：工具输出（日志/命令结果/网页抓取）是 Agent 输入 token 的最大来源，压缩工具输出 = 直接砍最大头

### 1.3 Paritok-4B: Intent-Conditioned Context Compression for Coding Agents
- **做法**：通用 prompt 压缩器按散文训练，对代码失效；此文训练「意图条件化」的代码上下文压缩小模型（4B），按任务意图保留代码关键片段
- **可抄点**：编程类 Agent 专用压缩模型；重复读大文件/工具输出是编码 Agent token 账单的支配项

### 1.4 SkillZip: Evaluation-Free Skill Compression for Self-Evolving Agents
- **做法**：自进化 Agent 的技能库会重复堆叠（同一要求在多个分支/示例/警告里反复出现），SkillZip 免评估地压缩技能库中的冗余结构
- **可抄点**：Skill/Prompt 库需要定期「去重压缩」——这与你知识库 CLAUDE.md 里的 stale 标记机制同理

### 1.5 ContextWeaver: Selective and Dependency-Structured Memory Construction
- **做法**：滑动窗口和单轮压缩都破坏长程依赖；按「依赖结构」选择性构建记忆——保留有依赖关系的关键节点
- **可抄点**：压缩不是删历史，是**保留依赖链**

### 行业佐证
- **FrugalPrompt**（Token Attribution）：用 token 归因分析识别输入中的低贡献片段后删除，降低上下文冗余
- **Latent Context Compilation**：把长上下文蒸馏成「紧凑可移植记忆」，解决压缩的分布外泛化问题

## 二、L2+L6 推理预算与自适应推理

### 2.1 Ares: Adaptive Reasoning Effort Selection for Efficient LLM Agents
- **做法**：思考型模型支持可配置推理档位（reasoning effort），Ares 按任务难度自适应选择档位——简单任务低档，复杂任务高档
- **可抄点**：给 Agent 每步设置「推理预算」；简单步骤强制低思考模式

### 2.2 BudgetThinker / Plan and Budget / ROI-Reasoning（预算感知推理）
- **共同做法**：预先估算任务所需计算量（元认知），给推理过程设预算控制 token（BudgetThinker 用控制 token 实现）；先规划再分配预算（Plan and Budget）
- **ROI-Reasoning 核心洞察**：模型不知道任务需要多少计算——预计算元认知让「每 token 的回报率」可优化

### 2.3 Spend Less, Reason Better: Budget-Aware Value Tree Search for LLM Agents
- **做法**：把测试时扩展（树搜索）当作**有限预算资源**管理，Agent 不能无限耗算力；价值感知的搜索在预算内选最优路径
- **可抄点**：给 Agent 的搜索/重试设硬预算上限，防止失败任务无限烧 token

## 三、L3 减少轮数：计划缓存与轨迹压缩

### 3.1 Cost-Efficient Serving of LLM Agents via Test-Time Plan Caching
- **做法**：Agent 的大量成本来自反复的规划与推理；把**计划（plan）缓存复用**——相似任务直接命中已验证的执行计划，跳过规划阶段
- **可抄点**：为高频任务维护「计划库」，相似请求先查计划再推理

### 3.2 Improving the Efficiency of LLM Agent Systems through Trajectory Reduction
- **做法**：软件工程类多轮 Agent 的轨迹冗余大；系统性地压缩轨迹（合并相邻步骤、删除无效轮次）
- **可抄点**：任务完成后对轨迹做「事后压缩」，压缩结果作为同类任务的 few-shot 示例（比原始轨迹短数倍）

### 3.3 Agent Capsules: Quality-Gated Granularity Control for Multi-Agent LLM Pipelines
- **做法**：N 个 Agent 流水线 = N 次调用；把多 Agent 合并成更少调用（compound execution）省 token，但盲目合并会悄悄劣化质量——**用质量门控决定合并粒度**
- **关键设计**：不是「能合就合」，是「质量门控通过才合」
- **可抄点**：多 Agent 系统先测「合并后质量不降」的阈值，再动态合并

## 四、L4 换便宜模型：级联与路由（文献最厚的一层）

### 4.1 奠基：FrugalGPT（斯坦福，2023，被引最高的降本工作）
- **三种策略**：①prompt 适配 ②**级联（cascade）**——便宜模型先答，带置信度评估，不确定再升级到贵模型 ③多模型 query 扫描
- **验证数据**：在部分基准上达到 GPT-4 级质量，同时**成本降低最高 98%**
- **地位**：级联/路由方向的开山之作，之后所有 routing 工作的对照基线

### 4.2 A Unified Approach to Routing and Cascading for LLMs（统一路由与级联）
- **做法**：路由（选一个模型）和级联（先便宜后升级）统一在一个框架里，按成本-性能联合优化
- **可抄点**：级联比纯路由更稳——路由选错没有兜底，级联有「升级」这个安全网

### 4.3 In-Context Distillation with Self-Consistency Cascades（**Training-Free 级联**）
- **做法**：免训练的级联——小模型多次采样 + 自一致性投票，置信度不够才升级大模型；同时用大模型输出作为小模型的 in-context 示例（上下文蒸馏）
- **可抄点**：**不需要训练**就能落地，Agent 原型期最实用的降本开关

### 4.4 Cluster, Route, Escalate: Cascaded Framework for Cost-Aware LLM Serving
- **做法**：查询先聚类→每簇配路由→不确定升级；生产环境友好的三段式

### 4.5 置信度信号系（Leveraging Uncertainty Estimation / Confidence Tokens / On-device Routing）
- **共同思路**：升级决策的依据是「不确定性估计」——token 置信度、自一致性、verifier 打分
- **警告文献**：How Robust Are Router-LLMs? —— 路由器在分布外查询上很脆弱；The Routing Plateau —— 路由精度有天花板，超过后收益递减
- **可抄点**：路由器需要定期用真实流量重训；关注 RouterBench / TwinRouterBench / RouteJudge 这些评测的更新

### 4.6 蒸馏路线：把强 Agent 的能力装进小模型
- **Distilling LLM Agent into Small Models with Retrieval and Code Tools（Agent Distillation）**：不只蒸馏答案，**蒸馏「工具调用轨迹」**——小模型学会何时检索、何时写代码；推理成本大幅降（小模型无需长思考链）
- **LiteGUI**：RL 蒸馏轻量 GUI Agent，端侧可跑
- **Scaling Small Agents Through Strategy Auctions**：小模型 Agent 集群 + 策略拍卖机制分配任务

### 4.7 EvoRoute: Experience-Driven Self-Routing LLM Agent Systems
- **做法**：多 Agent 系统里（LLM+工具+记忆模块）的路由不是静态的——从历史执行经验中**自学习路由策略**，越用越省

## 五、L5 复用计算：缓存系

### 5.1 VectorQ: Adaptive Semantic Prompt Caching with Vector Q-学习
- **做法**：语义缓存的核心难题是「相似度阈值怎么定」——固定阈值要么误命中（质量降）要么漏命中（省钱失败）；VectorQ 用向量 Q 学习**自适应调整每个查询的相似度阈值**
- **可抄点**：语义缓存值得上，但阈值必须动态

### 5.2 MeanCache: User-Centric Semantic Caching for LLM Web Services
- **做法**：面向 LLM Web 服务的用户侧语义缓存，联邦式语义匹配
- **行业佐证**：语义缓存已被 AWS、Microsoft 等大厂广泛采用（Key Collision Attack 一文的背景陈述）——**这是经过工业级验证的降本手段**
- **安全提醒**：Key Collision Attack 揭示语义缓存可被碰撞攻击利用（恶意构造相似查询窃取缓存）——生产环境要加访问控制

### 5.3 IC-Cache: In-context Caching
- **做法**：服务端的 in-context 缓存，减少重复上下文的重复计算

### 5.4 平台层免费午餐
- 各家 API 的 **prompt caching / 前缀缓存**（OpenAI、Anthropic、DeepSeek 都支持）：系统提示词、few-shot、长文档放前缀，缓存命中部分按 1 折计价——**零设计成本，立省 50-90% 输入费**

## 六、系统级方法论

### 6.1 A Survey of Context Engineering for Large Language Models（上下文工程综述）
- 把「给模型看什么」上升为正式学科：写入（write）/选择（select）/压缩（compress）/隔离（isolate）
- **是本报告所有 L1 方法理论总纲**

### 6.2 DSPy（斯坦福，声明式 LM 管线编译）
- **做法**：不手写 prompt，声明任务签名 + 评估指标，由编译器自动优化 prompt 和 few-shot 选择
- **验证**：多篇对比研究证实 DSPy 优化后的管线在更少 token 下达到或超过手工 prompt
- **可抄点**：prompt 不是写出来的，是**编译出来的**——用 MIPROv2 等 optimizer 自动搜索最小有效 prompt

### 6.3 Bayesian Orchestration of Multi-LLM Agents（成本感知序贯决策）
- **做法**：把「每步用哪个模型」建模为**不对称错误成本**的贝叶斯序贯决策（漏报成本 vs 误报成本不同）
- **可抄点**：不同步骤的错误代价不同——关键步骤用强模型，容错步骤用弱模型，用错误成本矩阵形式化

### 6.4 Routine: Structural Planning Framework for Enterprise Agent（企业级结构化规划）
- **做法**：通用模型缺领域流程知识导致规划混乱多绕路；把领域流程**结构化（Routine）**后注入，减少无效轮次

## 七、落地路线图（按 ROI 排序的实施顺序）

### 第一阶段：零成本开关（1 天内，预计省 30-60%）
1. **开前缀/prompt 缓存**：系统提示+few-shot 前置，命中的输入按 1 折计费
2. **接语义缓存**：高频相似问（客服/查询类 Agent 命中率可达 30-70%），用 VectorQ 式动态阈值
3. **关掉不必要的 thinking 档**：简单步骤强制低推理档

### 第二阶段：输入瘦身（1-2 周，再省 20-40%）
4. **工具输出压缩**：日志/网页/命令输出过一遍结构化摘要再进历史
5. **记忆编译**：对话历史 → 结构化记忆（参考 11× 缩减案例）
6. **Skill/Prompt 库去重**：定期压缩冗余（SkillZip 思路）
7. **DSPy 编译 prompt**：用 optimizer 找最小有效 prompt

### 第三阶段：混合模型（2-4 周，再省 40-70%）
8. **Self-Consistency 级联**（免训练）：小模型投票，置信不够升大模型（FrugalGPT 路线）
9. **错误成本矩阵**：按步骤重要性分配模型档位
10. **计划缓存**：高频任务沉淀已验证执行计划

### 第四阶段：长期资产（1-3 月）
11. **Agent 蒸馏**：把成熟 Agent 的轨迹蒸馏进小模型（含工具调用轨迹，不是只蒸馏答案）
12. **经验驱动自路由**：像 EvoRoute 一样让路由策略从历史流量中自学习

### 配套的「质量护栏」（保证质量不降的关键）
- **门控评估**：每次降本改动（合并 Agent/换模型/加压缩）必须过质量门控（Agent Capsules 的教训：盲目合并悄悄劣化）
- **抽样人工审查**：论文四步循环之外的第五步——成本下降时质量可能静默下滑，定期人工抽查（呼应 WikiSkill 的 Gating + 人工审计）
- **双指标监控**：成本和任务成功率必须一起看，单看成本会退化成「便宜的垃圾」

## 八、已验证效果速查表

| 方法 | 出处 | 验证效果 | 落地难度 |
|---|---|---|---|
| 级联+置信升级 | FrugalGPT (Stanford) | 最高省 **98%** 保持质量 | 中 |
| 自一致性级联（免训练） | In-Context Distillation w/ Self-Consistency Cascades | 显著降本，免训练 | **低** |
| 结构化记忆蒸馏 | Structured Distillation | token **↓11×**，检索不损 | 中 |
| 语义缓存 | VectorQ / MeanCache（AWS/Microsoft 采用） | 命中率 30-70%（场景相关） | 中 |
| 前缀缓存 | 各 API 平台 | 输入费用 ↓50-90% | **极低** |
| 计划缓存 | Test-Time Plan Caching | 跳过规划轮 | 中 |
| DSPy prompt 编译 | Stanford NLP | 更少 token 达同质量 | 中 |
| Agent 蒸馏（含工具轨迹） | Agent Distillation (OSU) | 小模型替代大模型推理 | 高 |
| 质量门控合并 | Agent Capsules | N 次调用→更少，质量门控保底 | 中 |
| 预算感知搜索 | Spend Less, Reason Better | 防失败任务无限烧钱 | 中 |
